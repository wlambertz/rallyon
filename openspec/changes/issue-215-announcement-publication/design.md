# Design

## Context and constraints

Tournament Management owns a minimal announcement associated with an existing tournament. #212's case demonstrates the form of an announcement, not verified demand or a complete legal template. The maintainer selected a public link for the first channel. The organizer UI, federation exchange and registration are outside this change.

The current draft PUT is authentication-only and accepts updates without a creator comparison (see `tournament-draft-update` specification and `DraftReplacement.kt`). Therefore creator-only publication of whatever draft happens to contain would trust data another authenticated user could change. Avoid that dependency: the creator submits the announcement content explicitly on publication and each correction; do not automatically copy draft fields.

## Decisions and tradeoffs

- Use a dedicated announcement with title (maximum 200 characters), start/end instants, venue text (maximum 500 characters) and a plain-text body (maximum 10,000 characters). Body covers optional event information in organizer-provided prose; do not promise automatic compliance or sanitize it into HTML. Clients must render text as text. No media, automatic imports or individual regulatory field rules.
- Before persistence, reject U+0000 in text and event instants outside PostgreSQL's supported range (4713-01-01 BC 00:00:00 to 294276-12-31 AD 23:59:59.999999 UTC, inclusive) with a 400 response, preserving any prior snapshot. This prevents database errors for unrepresentable input.
- Use authenticated creator-only operations for initial publication, full replacement, withdrawal and management read. Compare the authenticated positive `rallyon_user_id` to stored `createdByUserId`; do not use the request's organizer ID as proof. This deliberately limits shared organizer work; transferring ownership is out of scope. Keep existing draft authorization unchanged and explain its independent risk.
- Provide a stable GET-only public link for the published announcement, rendered as readable UTF-8 `text/plain`, with `X-Content-Type-Options: nosniff`. Construct it from an explicit allowlist without creator identifiers, roster, configuration or withdrawn content; never interpret user text as HTML. No search/list endpoint or cache/CDN is included; use `Cache-Control: no-store` for corrections and withdrawals.
- The announcement has its own creator-controlled published/withdrawn state, independent of tournament draft visibility. A tournament becoming PRIVATE does not hide an already published announcement: the creator must explicitly withdraw it. Draft visibility changes cannot reactivate it. Withdrawal retains the snapshot, advances its version and hides it; a full creator-authorized replacement using the current withdrawn version explicitly republishes it. The management read lets the creator recover that version. Communicate this separation prominently to the organizer.
- Keep announcement version separate from tournament version. Initial creation requires no existing announcement; correction, withdrawal and republication require the current announcement version. Database uniqueness and optimistic locking protect concurrent initial writes and updates; reject absent/stale preconditions and losing writes without partial updates. Return one current snapshot, version and last-publication timestamp. No revision history, email notification or cross-system correction propagation is promised.
- The single public content route must not make other methods or sibling paths anonymous. Service-specific security configuration must restrict anonymous access to exactly the read operation, preserve existing JWT issuer/audience/claims, and test unauthenticated writes, path variants, invalid JWTs and existing endpoints. The shared starter's `permitAll` entries are path patterns without method restriction; do not simply add a broad pattern there and assume GET-only access.
- Proposed HTTP contract: `POST /api/tournamentmgmt/announcements/{tournamentId}` creates; `PUT` on the same resource replaces or explicitly republishes with numeric `If-Match`; `DELETE` withdraws with numeric `If-Match`; `GET` provides the public plain-text view. A separate authenticated `GET /api/tournamentmgmt/announcements/{tournamentId}/management` gives only the creator the snapshot, state and version, including when withdrawn. Use 201 for creation, 200 for correction, withdrawal and reads, 400 for invalid content or a malformed/missing precondition, 401 for anonymous writes or management reads, 403 for an authenticated noncreator, 404 for missing/unpublished/withdrawn public reads and 409 for existing or stale/conflicting writes. A valid authenticated caller with no usable numeric identity is rejected without saving. The public link contains the tournament ID and is discoverable by anyone who obtains it; it is not a secret or access token.

## Bounded contexts, invariants and dependency direction

Implement the announcement inside existing `setup.configuration` with framework-free domain and use-case logic behind a port, plus web and JPA adapters. A publication refers to the tournament by ID and checks its immutable creator. Enforce content validity, one current snapshot per tournament, creator authority and independent publication-state and version invariants. Tournament draft visibility must never mutate the announcement state. No new event or cross-context dependency is required. Confirm aggregate ownership and transaction strategy in an ADR before implementation, including a concrete locking/isolation approach for concurrent announcement mutations.

## Compatibility and escalation assessment

New contracts are additive; the existing `/api/tournamentmgmt/config` semantics and JWT checks remain unchanged. Anonymous exposure is a security-sensitive service configuration change requiring explicit approval and review. An append-only Flyway migration for the snapshot and version is expected and requires explicit escalation; the exact next version must be established at implementation. Existing data must remain readable, with no announcement implicitly created for existing tournaments. No changes to `3rd_party/iam`, new dependencies, modules or external integrations are planned. If any prove necessary, stop and escalate.

## Validation, rollout and recovery

Use domain tests for validation, authority and conflicts; controller/security tests for exact method/path restrictions, literal plain-text rendering and no data leaks; concurrent persistence tests and PostgreSQL/Flyway migration verification for uniqueness and version races. Test stable public reads, no-store/nosniff headers, withdrawal, explicit republication, management recovery and independence from tournament visibility changes by any authenticated user. Run IAM install when needed, then `./service/tournamentmgmt/mvnw -B -f service/tournamentmgmt/pom.xml clean verify`, plus `npm run format:check`. Confirm the actual PostgreSQL test environment rather than treating H2 as equivalent. Roll out the additive migration and service together; rollback must be planned without rewriting migrations or deleting user content.

## ADR assessment

An ADR is needed: this introduces an announcement consistency boundary, independent publication state/version and controlled anonymous read in Tournament Management. It must document the alternative of publishing directly from the mutable draft, the existing authorization limitation, independent visibility, exact transaction boundaries and the future Public Information context. ADR acceptance occurs before implementation, not by this draft alone.
