## Candidate smallest next step

Recommend refining a **creator-prepared, versioned participant field for one bracket**, before a format-dependent draw generator. The organizer would deliberately select eligible ACCEPTED entry records and retain their single/pair member snapshots and source revisions. The field must distinguish membership readiness from playing eligibility and from a published draw. Its naming, selection rules, capacity policy, configuration compatibility and change/withdrawal treatment remain decisions for the next full lifecycle, not requirements adopted here.

This bounded bridge uses existing evidence (an entry is not a roster, local keys do not map to global numeric references) without requiring a player directory, federation integration or results engine. Organizer value is plausibly high, player value medium, spectator value low until publication; effort is provisionally medium because persistence, versioned selection and privacy still need design. These are research estimates without user interviews or a numerical budget.

A subsequent single-elimination preview could be comparatively small once the competition, entrant units, format identity, seed policy, bye policy, random/lot provenance and repeatable input snapshot are selected. No current pure-KO enum value or accepted draw spec can be assumed. Groups-to-KO is a larger alternative because it adds fixtures, result ownership, ordered standings, progression and correction effects; reuse #203 instead of embedding those decisions in a first generator.

## Ownership, ADR and compatibility decisions

- Candidate owner: Tournament Management, with a distinct field/draw boundary from editable configuration and the entry book. `docs/architecture/context-map.md` remains a draft; whether this belongs in existing `setup.configuration`, `setup.phases` or a new module requires an ADR before implementation depends on it.
- Preserve Dependency Rule and published `api` boundaries. No external context reads another context's tables. Global participant identity, ranking sources, Scoring transport and result authority remain unresolved; this research creates none of them.
- A first field snapshot can retain unverified tournament-local identities, subject to explicit approval and privacy policy. It cannot claim federation eligibility, partnership consent or account linkage. Capacity and duplicate/conflicting-member decisions must be specified rather than inferred from source text.
- Record the organizer's selection inputs, source book revision, field revision, rules/version and any explicit lot/random decisions needed by a future draw. Whether entry correction/withdrawal blocks, invalidates or merely flags a prepared field must be decided. Regeneration must not silently replace a published or running draw.
- Persistent fields/draws likely need an additive migration and explicit retention/rollback assessment; a new context/module/dependency or API/JWT break requires lifecycle escalation. No such production changes are made or approved by this research. Preserve legacy `/api/tournamentmgmt/...`, JWT and `ro` behavior.
