# OpenSpec Skill

RallyOn uses [OpenSpec](https://openspec.dev) (Fission-AI, pinned in `docs/adr/0002-adopt-openspec-dev.md`) for spec-driven changes. This skill holds only the RallyOn-specific rules; the mechanics live in the generated skills.

## Which skill to use

| Intent                                  | Skill                     |
| --------------------------------------- | ------------------------- |
| Think through an idea, no artifacts yet | `openspec-explore`        |
| Create a change with all artifacts      | `openspec-propose`        |
| Revise an existing change's plan        | `openspec-update-change`  |
| Implement the tasks of a change         | `openspec-apply-change`   |
| Merge delta specs into `openspec/specs` | `openspec-sync-specs`     |
| Finish a change                         | `openspec-archive-change` |

`.agents/skills/openspec-*` is generated by `openspec init/update` and is Prettier-ignored. Do not hand-edit it; put RallyOn rules here or in `openspec/config.yaml`.

## Read before proposing

1. Root `AGENTS.md` and the nearest nested `AGENTS.md` for the affected area.
2. The area skill (`tournamentmgmt-service`, `keycloak-auth`, `ro-cli`).
3. `docs/clean-architecture-and-clean-code.md` and `docs/adr/` for boundaries a spec must respect.
4. `openspec/config.yaml` for the project rules injected into every artifact.

## RallyOn rules

- Specs live in top-level `openspec/`. Do not write new specs under `docs/wiki/`.
- Write requirements in the domain's own terms (Modulith module names, existing `api` value types), not in endpoint or table terms, unless the contract itself is the REST endpoint or JWT claim.
- Every requirement needs at least one testable `#### Scenario:` (WHEN/THEN). Add failure and security scenarios where auth, roles or `rallyon_user_id` are involved.
- State backward-compatibility explicitly for `/api/tournamentmgmt/...`, JWT claims and role names, and `ro` commands (see root `AGENTS.md` Change Policy).
- Flag any Flyway migration, `3rd_party/iam` change, new dependency or new module in `design.md`; these need human review before apply.
- Planning boundary: propose/explore/update write planning artifacts only. Implementation starts with `openspec-apply-change` after the user has reviewed the artifacts.
- Do not create GitHub issues or commit as part of proposing. Use `issue-implementation-planner` and `commit-messages` when the user asks.
- `application/organizer` has no frontend stack yet; changes that need UI are blocked on the decision described in `organizer-ui`.

## Legacy openspec.tech specs

`docs/wiki/specs/**/*.yaml`, `ro spec create|validate|view` and the openspec.tech schema are superseded but still present until the existing specs are migrated to `openspec/specs/`. Keep `ro spec` behaviour unchanged (CLI compatibility); do not add new YAML specs. See ADR 0002.

## Local commands

```bash
npx -y @fission-ai/openspec@1.14.2 --version
npx -y @fission-ai/openspec@1.14.2 validate --all
npx -y @fission-ai/openspec@1.14.2 update   # regenerates .agents/skills/openspec-*
```

## Validation

- `openspec validate --all` for specs and changes touched.
- `npm run format:check` for the docs and config touched (generated skills are ignored).
